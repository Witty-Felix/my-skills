# 会议纪要专业总结

当用户要求总结会议记录、整理会议转写稿、生成正式会议纪要，且希望输出中文 Word 文档时，按本流程执行。目标是把原始会议内容整理为事实忠实、可追溯、可执行的正式纪要，而不是逐句改写的聊天摘要。

加载 @references/minutes-standard.md 获取会议结构、提炼规则和文档模板。  
加载 @references/glossary-workflow.md 获取专有词收集、受控校对和核对说明规则。  
加载 @references/word-delivery.md 获取 Word 文档交付、排版和验收规则。  
加载 @references/docx-generation.md 获取 python-docx 工程实现、风格基线、导出后回读校验与相对时间处理。  
加载 @references/degradation.md 获取输入缺失、解析失败和导出失败时的处理方式。

## 适用输入

1. 接收会议录音转写稿、会议原始记录、聊天记录导出文本，或用户提供的本地会议文档。
2. 先识别输入格式、文件可读性和可提取的会议基本信息。
3. 处理本地 Office 文档内容前，先按当前宿主的本地文档路由要求选择可用的读取与导出能力。
4. 输入不完整时，只处理可确认内容；不要补写缺失的时间、参会人、数字、负责人、截止日期或结论。

## 会议专有词校对

1. 先通读全文，自行扫描疑似同音、近音、英文大小写与分词误识别，形成“疑点清单”。
2. 用 AskUserQuestion 让用户三选一：① 直接按原文整理，疑点全部列入核对说明标“待核对”；② 按上下文保守校正，仅统一高置信产品名，人名与内部简称保留原文；③ 由用户补充专有词表后再出稿。
3. 用户选择补充词表时，把“疑点清单”以表格形式发给用户填写，列：序号 / 转写原文 / 我的判断 / 正确写法。用户可以对不确定的行回“先告诉我出自哪里，我再判断”——此时必须**连同上下文引用原句**回给用户，并把该词保留原文、标“待核对”，不得自行裁决。
4. 依次收集：人名、团队或公司名、客户名、项目或产品名、技术或行业词、业务词、内部简称，以及容易听错的写法。
5. 把用户提供的标准词仅作为本次会议的核对词库，不把它们当作会议事实。
6. 只有在原始记录存在同音、近音、大小写或分词误识别，且上下文足以支持时，才统一成标准词。
7. 人名、数字、日期、金额、比例和承诺采取更严格标准。证据不足时保留原文，不替换。
8. 相对时间不换算：原文只说“明天 / 后天 / 这两天”而未给日期时，写“会议次日（原文「明天」）”，并在待确认事项中单列一条“会议日期未标注”。
9. 记录发生的关键修正及依据；不确定的疑似错误列入“名称与术语核对说明”，状态写“待核对”。
10. 用户要求新增、修改或保存常用词库时，先列出具体变更并取得明确确认后再写入词库。没有确认时，只把词汇用于本次任务。

## 内容重组

1. 过滤纯游戏、破冰、抽奖、娱乐互动与无关闲聊。
2. 若被过滤内容中产生了业务结论、任务分配、风险或方向判断，只保留这些有效工作信息，不记录玩法或闲聊过程。
3. 按会议推进顺序划分阶段：一位主要讲话人连续主导表达为一个阶段；多位人员围绕同一问题集中交流为一个“多人讨论阶段”。
4. 短暂插话、追问或补充不机械拆分阶段；议题明显切换、主讲人明显更替或讨论由单人主讲转为多人集中讨论时才切分。
5. 为每个阶段确定简洁、事实性的标题。单人阶段采用“姓名：主题”，多人阶段采用“集中讨论：主题”。
6. 每个阶段概括讨论内容与形成状态，并在本阶段内保留对应的“核心观点”和“原话摘录 / 金句”。
7. 不设置全文汇总的“核心观点”或“金句”章节。核心观点与原话必须留在其发生的单人或多人讨论阶段，保留语境和来源。
8. “核心观点”只收录明确的判断、原则、方向或共识；“原话摘录 / 金句”只收录表达有代表性且不改变原意的原话。发言人不明确时写“多人讨论中的代表性表达”，不要擅自归属个人。

## 管理摘要与关联编号

1. 在阶段纪要之前生成“管理摘要”，仅包括：团队当前问题、未来展望与方向、行动项总表、风险与待确认事项。
2. 行动项总表是所有待办信息的唯一正式来源。每项分配唯一编号，如 A-01；待确认事项用 R-01。
3. 阶段内不重复完整待办或待确认内容，只以“关联事项：A-01、R-01”引用对应编号；没有关联事项则不添加该行。
4. 只把原文中明确提出、承诺或分配的事项写入行动项总表。原文没有负责人、截止时间或交付物时，填写“待确认”。
5. 讨论意见、猜测和备选方案不能写成决议或正式待办。原文出现“可能、考虑、看看、再讨论”等不确定表述时，在纪要中保留不确定性。
6. 原文存在冲突时，分别记录并标为待核对，不擅自选择其中一个版本。

## Word 文档交付

1. 输出一份结构严谨的中文 Word 文档（.docx），不用普通聊天正文替代最终交付。
2. 采用正式标题层级、语义化表格、白底深蓝正文（`1F3864`）、浅蓝表头与边框（`D9E2F3` 底纹 / `9DC3E6` 边框）的克制蓝色系风格（配色基线见 @references/docx-generation.md）。
3. 文档固定结构为：会议概览、管理摘要、分阶段会议纪要、名称与术语核对说明。
4. 在生成前检查：会议事实、数字、专名、结论、行动项编号以及阶段关联是否与原始记录一致。
5. 导出后用 python-docx 回读校验（脚本见 @references/docx-generation.md）：文件可打开、标题层级完整、表格列未缺失、A/R 编号唯一且连续无缺号、阶段数符合预期、阶段内没有重复的完整待办表、误识别词仅残留于“名称与术语核对说明”的“原始转写”列。
6. 向用户交付 .docx 文件，并说明已校正项、待核对项（逐条给出原文出处，便于用户判断）与任何降级限制。
7. 生成 .docx 后，用同一份行动项 / 待确认项数据源（单一来源，Word 与 Excel 共用）立即导出「待办事项.xlsx」（openpyxl 实现，详见 @references/docx-generation.md）：含「待办事项」「待确认事项」两个工作表，蓝色系表头与边框、冻结标题行、启用筛选，并额外为待办事项增加「完成时间（跟踪）」列；交付时一并说明该 xlsx。

## 质量底线与停止条件

1. 不虚构原文没有的事实、数字、结论、负责人、时间或交付物。
2. 不把用户提供的词库中但原文未出现的词写进纪要。
3. 不为了精炼或修辞改变原话含义。
4. 不将个人建议写成团队决定。
5. 不在未确认时写入、覆盖或更新用户的常用词库。
6. 当原始记录无法读取、内容严重缺失，或无法可靠生成 .docx 且用户不接受结构化内容降级时，停止正式交付并说明缺失条件。
